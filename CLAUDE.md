# Claude Code — Project Guidelines

> Companion to `novospace.git/CLAUDE.md`. The code-style rules below are shared
> across both repos; keep them in sync if either changes.

## Code style

- **No hardcoded string duplication.** If a string literal (username, path prefix, domain, etc.) appears more than once in a file, extract it into a named constant at the top before finishing the edit. Apply this proactively — do not wait to be asked.
- **No logic duplication.** If two functions share the same sequence of operations, extract a helper immediately — do not wait to be asked. Symmetric operations (backup/restore, encode/decode, pack/unpack) are a strong signal.
- **Explicit `dest=` on hyphenated argparse flags.** Any `add_argument("--foo-bar", ...)` whose long flag contains a hyphen must pass `dest="foo_bar"` explicitly, so the CLI-flag→attribute mapping is spelled out at the call site (argparse converts `-`→`_` silently otherwise). Keep the flag itself hyphenated (Unix convention); only the `dest` is added. Flags with no hyphen (`--restore`, `--owner`) and positionals don't need it.
- **Order `add_argument()` calls alphabetically by long flag.** Within a parser, declare optional arguments in alphabetical order of their `--long-flag` name (ignore the leading dashes; `--datasets-dir` before `--display-name` before `--email` …). This keeps `--help` output and the call site scannable and gives new flags an obvious insertion point instead of being appended randomly. Positional arguments keep their semantically-required order (they are not reordered); only the optional `--flags` are alphabetized. A short comment at the top of the block (`# Arguments alphabetical by long flag (CLAUDE.md).`) is welcome but not required.
- **Import the module, qualify at the call site — for first-party modules.** Import our own modules as modules, not their individual names: write `from deploy import deployer` (or `from . import contract`) and call `deployer.NovospaceDeployer(...)`, `contract.Route(...)`. Do *not* `from deploy.deployer import NovospaceDeployer` — the bare name at the call site hides where it is defined. The goal is that the last path segment of the defining module appears at every use, so the origin is obvious at a glance. This applies to first-party modules (ours and sibling packages) only; idiomatic standard-library symbol imports stay as-is (`from pathlib import Path` → `Path(...)`, `from dataclasses import dataclass` → `@dataclass`, `from typing import Protocol`), since those names' origins are universally known and module-qualifying them is unidiomatic. A deliberate re-export is the one exception (e.g. `IMPORTANCE_WARNING = backend_monitor.IMPORTANCE_WARNING` to widen a module's public surface), and should be written as an explicit assignment so the intent is visible.
- **Blank comment line before code after a multi-line comment.** When an in-code comment block spans more than one line and immediately precedes the code it describes, insert an empty comment line (a bare `#` at the comment's indentation — not a blank source line) between the prose and that code, so the comment block is visually separated from the statement. Single-line comments need no separator. Example:
  ```python
  # First-ever run: establish the cursor without emailing a backlog (an
  # unbounded "everything since boot" digest would be the first thing the
  # operator sees). Subsequent runs cover [cursor, now].
  #
  if cursor is None:
  ```
- **ASCII-only in comments and docstrings.** Keep in-code comments *and* module/class/function docstrings to plain ASCII characters. Do not use non-ASCII glyphs (e.g. the arrow `→`, en/em dashes `–`/`—`, box-drawing `─`, smart quotes, `§`) inside them — some editors and terminals render them wrongly. Write `->` for an arrow, `-` for a dash, straight quotes, and spell out "section" instead of `§`. (This applies to code comments and docstrings; Markdown docs and genuine user-facing runtime strings — e.g. `print()` output — may use full Unicode.)
- **Comment the non-obvious "why," not the obvious "what."** A comment should capture intent or a constraint the code cannot express. Do *not*: restate what the next statement plainly does, repeat rationale already documented at the function/class being called, narrate a self-explanatory single statement (`i += 1  # increment i`), or pad with defensive `IMPORTANT:` / `NOTE:` prose. When a multi-line "why" block has drifted, trim it to the 1–3 lines that actually matter rather than leaving stale narration. The name and surrounding context usually convey the "what" already.
- **Close multi-line block comments on their own line.** For a C-style `/* ... */` block (TypeScript/JS) spanning multiple lines, put the closing `*/` on its own line, aligned under the opening `/*` — do not append it to the last sentence. Single-line `/* ... */` and `//` comments stay on one line. (The Python analogue is the blank-`#` separator rule above; both keep the comment block's boundary visually distinct from the code.)
- **Match the surrounding file's comment conventions.** Mirror the local style rather than introducing a new one: existing function/class doc-block format (e.g. JSDoc `@param`/`@returns`, Python docstring sections, `IN`/`OUT`/`INOUT` param markers where a file uses them), banner layout, and indentation. Consistency within a file outweighs personal preference.

## Git

- **Never commit automatically.** Always show the diff and wait for explicit user approval before running `git commit`. The user needs to verify changes before they land in history.
- **Short commit messages.** One concise line, no body. No `Co-Authored-By` trailer unless the user asks.
- **Keep executable scripts executable.** Scripts that ship with a shebang and `100755` mode (e.g. `tools/ops/*.py`, `database/gedcom_*.py`, `backend/run_dev_backend.py`, `tools/git-hooks/*`) must stay executable. After any commit touching them, verify with `git ls-files --stage <path>` that the mode is still `100755`; if it dropped to `100644`, run `git update-index --chmod=+x <file>` and commit immediately.
